# TIL: Scaling OSM-Based Weak Label Generation for Semantic Segmentation
_Date: 2026-02-24_

**Project Context:** Urban imagery segmentation (roads, buildings, water)  
**Tech Stack:** Python, Rasterio, GeoPandas, OSMnx, Shapely, tqdm  

---

## 🧠 The Problem

I needed to generate weak semantic labels (roads, buildings, water) from OpenStreetMap (OSM) for multiple neighborhoods.

Each neighborhood had:
- A 1km AOI GeoTIFF
- 16 tiled images (512 x 512 pixels)
- Two imagery sources

My initial approach queried OSM **per tile** and rasterized features individually.

### The issue:
- Too many Overpass API calls  
- Slow execution  
- Risk of rate limiting  
- Redundant downloads  
- Harder to maintain  

This didn’t scale.

---

## 💡 The Insight

Instead of querying OSM per tile, I switched to:

> **Query once per neighborhood AOI, rasterize once on the AOI grid, then tile the label raster using pixel windows.**

This reduced network calls dramatically and guaranteed pixel-perfect alignment.

---

## 🏗 Final Architecture

AOI.tif (1km)
↓
Download OSM features (roads, buildings, water)
↓
Rasterize on AOI grid
↓
weak_osm_aoi.tif
↓
Tile using rasterio Window
↓
tiles/<neighborhood>/labels/weak_osm/*.tif

---

## 🗺 Why Rasterize on the AOI Grid?

Rasterizing directly on the AOI GeoTIFF grid ensures:

- Identical CRS
- Identical resolution
- Identical affine transform
- Perfect tile alignment

I then used the same `rasterio.windows.Window` logic as the imagery tiling script.

This guarantees:

> Label tiles and image tiles are pixel-aligned without reprojection.

## 🧩 Exclusive Classes with Priority Rules

Classes:

| Value | Class      |
|-------|------------|
| 0     | Background |
| 1     | Road       |
| 2     | Building   |
| 3     | Water      |

Priority logic:

road → water → building

Meaning:
- Water overwrites roads
- Buildings overwrite both
- Ensures strictly exclusive labels

This makes later segmentation validation clean and unambiguous.

---

## Weak vs Gold Labels

I deliberately kept:

- `weak_osm/` → automatically generated labels
- `gold/` → manually corrected ground truth

Why?

Because evaluating a model on labels generated by the same model family (e.g., SAM) introduces bias.

Weak labels are scaffolding.  

Gold labels are truth.

---

## 🚀 Performance Improvements

Switching from per-tile queries to per-AOI queries:

- Reduced Overpass requests by ~16x per neighborhood
- Eliminated API throttling issues
- Simplified debugging
- Made the pipeline deterministic

I also added `tqdm` progress bars for better visibility during batch runs.

---

## 🛠 Engineering Lessons

### 1. Raster alignment > geographic clipping  
Pixel windows preserve exact grid alignment.

### 2. Query once, reuse many times  
Network calls are expensive — design around that.

### 3. Weak labels are not ground truth  
Separate them clearly in your pipeline.

### 4. Linting and type checking matter  
Fixing Ruff and type warnings early prevents silent bugs.

### 5. Architecture matters more than functions  
The biggest improvement came from restructuring the workflow — not from rewriting logic.
